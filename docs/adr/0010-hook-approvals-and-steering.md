# ADR 0010: Hook, approvals and steering

Status: Accepted for Slice 3.

The permission policy is pure core code (`antiquota_core::policy`). It ports the legacy decisions and shell parsing, with three deliberate corrections: operator runs made only of separators (a blank line, `;\n`, `&&\n`) split commands instead of hiding a second command inside the first; `>&` is allowed only for descriptor duplication; and combined force flags such as `git clean -fd` and `git branch -f` always ask. A permanent allow rule is refused for programs that run arbitrary programs or code (shells, `env`, `xargs`, `awk`, `sudo`, network fetchers, interpreters without a script, `command(*)`); such calls are approved one at a time. Deny lists accept any rule.

The `antiquota hook` subcommand runs before logging and the Tokio runtime and uses a blocking loopback HTTP client, so a local decision including process start takes milliseconds. It asks the engine named by `ANTIQUOTA_STATE` and long-polls a pending request in 25-second chunks. When no engine answers it applies the own-stack rules and refuses anything that needs a yes. When the engine answers `ask` for a session antiquota started (an unknown approval or session after a restart), the hook refuses the call: the HTTP contract still returns `ask`, but a skip-permissions run never proceeds unchecked. Calls without `ANTIQUOTA_SESSION` stay neutral for agy.

`serve` seeds the own stack and installs the `antiquota` hook entry for its own executable, keeping a user's `enabled: false`. The runner's preflight reads that entry: enabled and verified means every mode runs with skip-permissions; disabled by the user means agy's own modes apply, without native plan mode; missing or unusable refuses the launch. The verification runs the hook with an unreachable engine and requires a refusal.

Approvals live in the application service in memory, as in the legacy engine; pending and answered states are recorded as `approval` events and a stop declines all pending requests of the session. Arguments keep their nested structure, with strings over 4000 characters cut by a visible note. Steering drains only plain queued messages, expands `@path` mentions through the session store port, and records each as a `user` event with `steered: true`; the reducer never removes a queued item for a steered message. Steering stays in the approvals service until the features crate gains a mid-turn hook.
